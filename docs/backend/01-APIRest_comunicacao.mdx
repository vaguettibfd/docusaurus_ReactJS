## 1. O que é uma API?

A sigla **API** significa *Application Programming Interface*, ou Interface de Programação de Aplicações.

Uma API estabelece uma forma de comunicação entre diferentes sistemas ou componentes de software.

Por meio dela, uma aplicação pode solicitar informações ou executar operações disponibilizadas por outra aplicação.

Considere um sistema de cadastro de pessoas.

O usuário interage com uma interface para informar nome, e-mail, CPF ou CNPJ.

Entretanto, essa interface não precisa ser responsável pelo armazenamento definitivo dos dados.

Ela pode encaminhar as informações para um serviço especializado, que executará a operação solicitada.

Esse serviço disponibiliza uma API para que outras aplicações possam se comunicar com ele.

### 1.1. Exemplo de utilização

Imagine que um usuário deseja consultar as pessoas físicas cadastradas.

A aplicação poderá enviar uma solicitação para a API.

A API receberá a solicitação, consultará os registros disponíveis e retornará uma resposta.

O processo pode ser representado da seguinte maneira:

```text
       APLICAÇÃO CLIENTE
               |
               | Solicita os registros
               |
               v
          API REST
               |
               | Consulta os dados
               |
               v
        ARMAZENAMENTO
               |
               | Retorna os registros
               |
               v
          API REST
               |
               | Envia a resposta
               |
               v
       APLICAÇÃO CLIENTE
```

Observe que a aplicação cliente não precisa conhecer os detalhes internos do armazenamento.

Ela precisa conhecer apenas a forma correta de realizar a solicitação e interpretar a resposta.

Essa separação é uma das principais vantagens da utilização de APIs.

## 2. Compreendendo a arquitetura cliente-servidor

A comunicação com uma API REST normalmente envolve dois participantes principais: o **cliente** e o **servidor**.

### 2.1. Cliente

O cliente é a aplicação responsável por iniciar uma solicitação.

Pode ser, por exemplo:

- Uma aplicação web;
- Um aplicativo para dispositivos móveis;
- Um programa desenvolvido em outra linguagem;
- Uma ferramenta de testes de requisições HTTP.

Em nosso contexto, uma aplicação ReactJS poderá atuar como cliente da API de Pessoas.

Entretanto, neste material, utilizaremos também ferramentas que permitem realizar requisições diretamente, sem desenvolver uma interface.

### 2.2. Servidor

O servidor é responsável por receber as solicitações, processá-las e retornar respostas.

No caso da API de Pessoas, o servidor disponibiliza operações para consultar, cadastrar, atualizar e excluir registros.

Por exemplo, quando um cliente solicita a listagem de Pessoas Físicas, o servidor recebe a requisição e retorna os dados correspondentes.

### 2.3. Comunicação entre cliente e servidor

A comunicação acontece por meio de mensagens.

O cliente envia uma **requisição**, e o servidor retorna uma **resposta**.

```text
           CLIENTE                      SERVIDOR
              |                             |
              |-------- Requisição -------->|
              |                             |
              |       Processamento         |
              |                             |
              |<--------- Resposta ---------|
              |                             |
```

Essa comunicação é conhecida como modelo de **requisição e resposta** (*request-response*).

:::tip Importante

O cliente não precisa conhecer a implementação interna do servidor.

Para utilizar uma API, é necessário compreender quais operações estão disponíveis, como solicitá-las e como interpretar as respostas.

:::

## 3. O que é uma API REST?

REST é a sigla para *Representational State Transfer*.

Trata-se de um estilo arquitetural utilizado no desenvolvimento de sistemas distribuídos.

Uma API REST disponibiliza recursos que podem ser acessados e manipulados por meio de requisições HTTP.

Em nosso exemplo, os principais recursos são:

- Pessoas Físicas;
- Pessoas Jurídicas.

Cada recurso possui um endereço que permite identificá-lo.

Esses endereços são utilizados em conjunto com os métodos HTTP para indicar a operação desejada.

### 3.1. Recursos

Um recurso representa uma informação ou entidade disponibilizada pela API.

Por exemplo:

```text
/pf
```

representa o conjunto de Pessoas Físicas.

Já:

```text
/pj
```

representa o conjunto de Pessoas Jurídicas.

A API utiliza esses endereços para organizar o acesso aos dados.

### 3.2. Métodos HTTP

O método HTTP indica a operação que o cliente deseja executar.

Os principais métodos utilizados pela API de Pessoas são:

| Método | Finalidade |
|---|---|
| `GET` | Consultar informações |
| `POST` | Cadastrar um novo registro |
| `PUT` | Atualizar um registro existente |
| `DELETE` | Excluir um registro |

Observe que um mesmo endereço pode ser utilizado com métodos diferentes.

Por exemplo:

```http
GET /pf
```

solicita a listagem de Pessoas Físicas.

Já:

```http
POST /pf
```

solicita o cadastro de uma nova Pessoa Física.

A diferença entre essas operações está no método HTTP utilizado.

Estudaremos cada método com mais detalhes na próxima parte.

## 6. Compreendendo os endpoints

Um **endpoint** é um endereço disponibilizado por uma API para acessar determinado recurso ou operação.

Na API de Pessoas, temos endpoints para Pessoas Físicas e Jurídicas.

### 6.1. Endpoints de Pessoa Física

| Método | Endpoint | Finalidade |
|---|---|---|
| `GET` | `/pf` | Listar Pessoas Físicas |
| `GET` | `/pf/filtrar?nome=texto` | Filtrar Pessoas Físicas por nome |
| `POST` | `/pf` | Cadastrar Pessoa Física |
| `PUT` | `/pf/:id` | Atualizar Pessoa Física |
| `DELETE` | `/pf/:id` | Excluir Pessoa Física |

### 6.2. Endpoints de Pessoa Jurídica

| Método | Endpoint | Finalidade |
|---|---|---|
| `GET` | `/pj` | Listar Pessoas Jurídicas |
| `GET` | `/pj/filtrar?nome=texto` | Filtrar Pessoas Jurídicas por nome |
| `POST` | `/pj` | Cadastrar Pessoa Jurídica |
| `PUT` | `/pj/:id` | Atualizar Pessoa Jurídica |
| `DELETE` | `/pj/:id` | Excluir Pessoa Jurídica |

Observe que os endpoints apresentam uma organização semelhante.

A principal diferença está no recurso utilizado:

```text
/pf
```

ou:

```text
/pj
```

Isso permite manter um padrão de comunicação para os diferentes tipos de pessoa.

### 6.3. O significado de :id

Algumas rotas apresentam a expressão:

```text
:id
```

Esse elemento representa um parâmetro que deverá ser substituído pelo identificador de um registro.

Por exemplo:

```http
PUT /pf/675b2e1b7a9d48a52b7a0009
```

Nesse exemplo, o identificador informa qual Pessoa Física deverá ser atualizada.

O mesmo princípio será utilizado nas operações de exclusão.

:::tip Identificadores

Nos exemplos da API, os registros retornados apresentam um atributo chamado `_id`.

Esse identificador é utilizado para distinguir os registros armazenados no backend.

Nos capítulos anteriores, nossa aplicação com `localStorage` utilizava o atributo `id`.

É importante reconhecer essa diferença ao trabalhar com os dados retornados pela API.

:::

## 8. Compreendendo o formato JSON

As informações disponibilizadas pela API são representadas em formato JSON.

JSON significa *JavaScript Object Notation*.

Trata-se de um formato textual utilizado para representar dados estruturados.

Considere o exemplo:

```json
{
  "nome": "Ana Silva",
  "email": "ana@exemplo.com",
  "cpf": "12345678903"
}
```

Observe que as informações são organizadas em pares de chave e valor.

Por exemplo:

```json
"nome": "Ana Silva"
```

Nesse caso:

- `nome` representa a chave;
- `"Ana Silva"` representa o valor.

O JSON também permite representar objetos aninhados e listas.

### 8.1. Objetos aninhados

Considere uma pessoa que possui endereço:

```json
{
  "nome": "Ana Silva",
  "email": "ana@exemplo.com",
  "cpf": "12345678903",
  "endereco": {
    "cep": "71000-000",
    "logradouro": "Rua das Palmeiras",
    "bairro": "Centro",
    "cidade": "Brasília",
    "uf": "DF",
    "regiao": "Centro-Oeste"
  }
}
```

Observe que o atributo `endereco` contém outro objeto JSON.

Essa organização permite representar relacionamentos entre entidades.

### 8.2. Listas de objetos

Agora, considere o atributo `telefones`:

```json
{
  "nome": "Ana Silva",
  "telefones": [
    {
      "ddd": "61",
      "numero": "998887776"
    },
    {
      "ddd": "61",
      "numero": "33445566"
    }
  ]
}
```

Nesse exemplo, o atributo `telefones` contém um array.

Cada elemento do array representa um telefone.

Essa estrutura é semelhante à organização dos objetos utilizada em nossa aplicação ReactJS.

## 1. Como acontece a comunicação HTTP?

HTTP significa *Hypertext Transfer Protocol*, ou Protocolo de Transferência de Hipertexto.

É um protocolo utilizado para a comunicação entre clientes e servidores.

Quando uma aplicação deseja consultar ou modificar informações disponibilizadas por uma API REST, ela envia uma requisição HTTP.

O servidor recebe essa requisição, realiza o processamento necessário e retorna uma resposta.

Considere uma consulta à API de Pessoas:

```http
GET https://backend-pessoas.vercel.app/pf
```

Essa requisição solicita ao servidor os registros de Pessoas Físicas.

O processo pode ser representado da seguinte maneira:

```text
        CLIENTE                         SERVIDOR
           |                                |
           |   GET /pf                      |
           |------------------------------->|
           |                                |
           |        Processamento           |
           |                                |
           |   HTTP 200 + Dados JSON        |
           |<-------------------------------|
           |                                |
```

Observe que a comunicação possui dois momentos:

1. **Requisição:** o cliente solicita uma operação.
2. **Resposta:** o servidor informa o resultado da operação.

Essas mensagens possuem uma estrutura que estudaremos a seguir.

## 2. Estrutura de uma requisição HTTP

Uma requisição HTTP é composta por elementos que permitem ao servidor compreender qual operação deverá ser executada.

Os principais elementos são:

- Método HTTP;
- Endereço do recurso;
- Cabeçalhos (*headers*);
- Corpo da requisição (*body*), quando necessário.

Considere o exemplo de uma requisição para cadastrar uma Pessoa Física:

```http
POST /pf HTTP/1.1
Host: backend-pessoas.vercel.app
Content-Type: application/json

{
  "nome": "Ana Silva",
  "email": "ana@exemplo.com",
  "cpf": "12345678903"
}
```

Esse exemplo apresenta uma representação didática da mensagem HTTP.

Vamos compreender cada elemento.

### 2.1. Método HTTP

O método indica a operação que desejamos executar.

No exemplo, utilizamos:

```http
POST
```

Esse método é utilizado para solicitar a criação de um novo recurso.

### 2.2. Endereço do recurso

O endereço identifica qual recurso será utilizado.

No exemplo:

```text
/pf
```

representa o conjunto de Pessoas Físicas.

A URL completa será:

```text
https://backend-pessoas.vercel.app/pf
```

### 2.3. Cabeçalhos HTTP

Os cabeçalhos fornecem informações adicionais sobre a requisição.

Observe:

```http
Content-Type: application/json
```

Esse cabeçalho informa que o corpo da requisição está representado em formato JSON.

### 2.4. Corpo da requisição

O corpo contém os dados enviados ao servidor.

No exemplo:

```json
{
  "nome": "Ana Silva",
  "email": "ana@exemplo.com",
  "cpf": "12345678903"
}
```

Essas informações serão utilizadas para solicitar o cadastro de uma nova Pessoa Física.

:::tip Requisições com e sem corpo

Nem toda requisição HTTP precisa apresentar um corpo.

Uma consulta utilizando `GET`, por exemplo, normalmente não necessita enviar um JSON.

Já uma operação de cadastro utilizando `POST` precisa informar os dados do registro que será criado.

:::

---

## 3. Estrutura de uma resposta HTTP

Após processar a requisição, o servidor retorna uma resposta.

Uma resposta HTTP normalmente apresenta:

- Código de status;
- Cabeçalhos;
- Corpo da resposta, quando houver.

Considere o exemplo ilustrativo:

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
  "_id": "675b2e1b7a9d48a52b7a0009",
  "nome": "Ana Silva",
  "email": "ana@exemplo.com",
  "cpf": "12345678903"
}
```

### 3.1. Código de status

O código informa o resultado do processamento.

No exemplo:

```http
201 Created
```

indica que um novo recurso foi criado.

### 3.2. Cabeçalhos da resposta

Os cabeçalhos também podem informar características da resposta.

Por exemplo:

```http
Content-Type: application/json
```

indica que o conteúdo retornado está representado em JSON.

### 3.3. Corpo da resposta

O corpo contém os dados retornados pelo servidor.

Observe que o exemplo apresenta o atributo:

```json
"_id": "675b2e1b7a9d48a52b7a0009"
```

Esse atributo representa o identificador do registro.

O documento da API utiliza `_id` para identificar os registros armazenados no backend.

:::note Identificadores

Os valores de `_id` apresentados neste material são exemplos.

Quando um registro é criado, o identificador retornado dependerá do processamento realizado pelo servidor.

:::

```json
[
```

## 6. Método POST — Criando registros

## 7. Método PUT — Atualizando registros

O método `PUT` é utilizado pela API de Pessoas para atualizar registros existentes.

Diferentemente do `POST`, precisamos informar qual registro deverá ser modificado.

Para isso, utilizaremos seu identificador.

Considere a rota:

```http
PUT /pf/:id
```

A expressão `:id` representa o identificador da Pessoa Física.

Por exemplo:

```http
PUT /pf/675b2e1b7a9d48a52b7a0009
```

O corpo da requisição deverá apresentar as informações que serão enviadas para atualização.

### 7.1. Exemplo de atualização

Considere o seguinte JSON:

```json
{
  "nome": "Ana Maria Silva",
  "email": "anamaria@exemplo.com",
  "cpf": "12345678903"
}
```

Esse exemplo solicita a atualização dos atributos informados.

O comportamento exato de atualização de atributos omitidos depende da implementação da API.

No documento original, os exemplos de `PUT` também apresentam objetos associados, como título eleitoral e inscrição estadual.

### 7.2. Atualização de Pessoa Jurídica

Para atualizar uma Pessoa Jurídica, utilizaremos:

```http
PUT /pj/:id
```

Por exemplo:

```http
PUT /pj/675b301b7a9d48a52b7a0012
```

Observe que a estrutura da rota é semelhante à utilizada para Pessoas Físicas.

A diferença está no recurso solicitado.

:::tip POST e PUT

Uma maneira simples de diferenciar essas operações é observar sua finalidade:

- `POST /pf`: solicita a criação de uma Pessoa Física;
- `PUT /pf/:id`: solicita a atualização de uma Pessoa Física identificada por `id`.

Na API estudada, a atualização utiliza o método `PUT`.

:::

## 8. Método DELETE — Excluindo registros

O método `DELETE` é utilizado para solicitar a exclusão de um recurso.

Na API de Pessoas, utilizaremos:

```http
DELETE /pf/:id
```

para excluir uma Pessoa Física.

Para excluir uma Pessoa Jurídica, utilizaremos:

```http
DELETE /pj/:id
```

Observe que a operação depende do identificador do registro.

### 8.1. Exemplo de exclusão

Considere:

```http
DELETE /pf/675b2e1b7a9d48a52b7a0009
```

Essa requisição solicita a exclusão da Pessoa Física identificada pelo valor informado.

A exclusão é uma operação que modifica os dados armazenados no servidor.

Por isso, devemos utilizá-la com cuidado.

## 9. Parâmetros de rota

Algumas operações precisam identificar um registro específico.

Para isso, utilizamos parâmetros de rota.

Considere:

```text
/pf/:id
```

Nesse exemplo, `:id` representa um valor que será informado pelo cliente.

Se o identificador do registro for:

```text
675b2e1b7a9d48a52b7a0009
```

a rota utilizada será:

```text
/pf/675b2e1b7a9d48a52b7a0009
```

Observe que o identificador faz parte do caminho da URL.

Esse tipo de informação é chamado de **parâmetro de rota**.

Na API de Pessoas, os parâmetros de rota são utilizados nas operações de atualização e exclusão.

## 10. Parâmetros de consulta — Query Parameters

Além dos parâmetros de rota, uma URL pode apresentar parâmetros de consulta.

Esses parâmetros são utilizados para fornecer informações adicionais à operação solicitada.

Na API de Pessoas, podemos utilizar um parâmetro para filtrar registros pelo nome.

Considere:

```http
GET /pf/filtrar?nome=ana
```

Nesse exemplo:

- `/pf/filtrar` identifica o endpoint;
- `?` inicia a lista de parâmetros de consulta;
- `nome` identifica o parâmetro;
- `ana` representa o valor informado.

A URL completa será:

```text
https://backend-pessoas.vercel.app/pf/filtrar?nome=ana
```

### 10.1. Filtrando Pessoas Jurídicas

O mesmo recurso está disponível para Pessoas Jurídicas:

```http
GET /pj/filtrar?nome=tech
```

URL completa:

```text
https://backend-pessoas.vercel.app/pj/filtrar?nome=tech
```

O documento da API informa que o filtro realiza uma busca parcial, sem diferenciar letras maiúsculas e minúsculas.

Isso significa que uma pesquisa por:

```text
tech
```

poderá localizar registros com nomes como:

```text
Tech Soluções
```

ou:

```text
TECH SERVIÇOS
```

A documentação também informa que os resultados são organizados em ordem alfabética pelo nome.

### 10.2. Diferença entre parâmetros de rota e consulta

| Característica | Parâmetro de rota | Parâmetro de consulta |
|---|---|---|
| Exemplo | `/pf/123` | `/pf/filtrar?nome=ana` |
| Finalidade | Identificar um recurso | Informar critérios de consulta |
| Localização | Caminho da URL | Após o símbolo `?` |
| Utilização na API | Atualização e exclusão | Filtro por nome |

:::info Observação

Os parâmetros de consulta também são conhecidos como *query parameters*.

Eles são especialmente úteis em operações de pesquisa e filtragem.

:::

## 11. Cabeçalhos HTTP

Os cabeçalhos HTTP permitem transmitir informações adicionais sobre uma requisição ou resposta.

Um dos cabeçalhos mais importantes para nossa API é:

```http
Content-Type: application/json
```

Esse cabeçalho informa que os dados enviados no corpo da requisição estão representados em JSON.

### 11.1. Content-Type

Considere uma operação de cadastro.

O cliente envia:

```http
POST /pf HTTP/1.1
Host: backend-pessoas.vercel.app
Content-Type: application/json
```

Em seguida, apresenta o corpo JSON.

O servidor utiliza essa informação para interpretar o formato dos dados recebidos.

### 11.2. Accept

Outro cabeçalho comum é:

```http
Accept: application/json
```

Ele informa que o cliente deseja receber uma representação JSON.

Observe a diferença:

| Cabeçalho | Finalidade |
|---|---|
| `Content-Type` | Informa o formato do conteúdo enviado |
| `Accept` | Informa o formato de resposta desejado |

:::tip Atenção

O documento da API informa que as requisições com corpo utilizam `application/json`.

O cabeçalho `Accept` foi apresentado aqui como conceito geral de HTTP; o documento não estabelece que seja obrigatório para utilizar essa API.

:::

## 12. Códigos de status HTTP

Quando o servidor processa uma requisição, ele retorna um código de status.

Esse código informa o resultado da operação.

Os códigos são organizados em grupos.

| Grupo | Significado geral |
|---|---|
| `2xx` | Operação bem-sucedida |
| `3xx` | Redirecionamento |
| `4xx` | Erro relacionado à requisição |
| `5xx` | Erro relacionado ao servidor |

Vamos conhecer os códigos mais relevantes para a API de Pessoas.

### 12.1. Status 200 — OK

O código `200` indica que a requisição foi processada com sucesso.

É frequentemente utilizado em operações de consulta.

Por exemplo:

```http
GET /pf
```

pode retornar:

```http
200 OK
```

acompanhado dos registros solicitados.

### 12.2. Status 201 — Created

O código `201` indica que um recurso foi criado.

O documento da API apresenta esse status nos exemplos de cadastro de Pessoas Físicas e Jurídicas.

Por exemplo:

```http
POST /pf
```

pode retornar:

```http
201 Created
```

### 12.3. Status 400 — Bad Request

O código `400` indica que o servidor não conseguiu processar a requisição devido a um problema nos dados enviados.

O documento da API apresenta como exemplo a ausência de campos obrigatórios no corpo da requisição.

### 12.4. Status 404 — Not Found

O código `404` indica que o recurso solicitado não foi encontrado.

Na documentação da API, esse erro é associado à tentativa de atualizar ou excluir um registro inexistente.

### 12.5. Status 500 — Internal Server Error

O código `500` indica que ocorreu um erro interno no servidor.

O documento apresenta como possíveis exemplos problemas de conexão com o MongoDB ou falhas no DAO do backend.

### 12.6. Resumo dos códigos

| Código | Significado | Exemplo |
|---|---|---|
| `200` | Requisição bem-sucedida | Consulta realizada |
| `201` | Recurso criado | Cadastro realizado |
| `400` | Dados inválidos | Campo obrigatório ausente |
| `404` | Recurso não encontrado | ID inexistente |
| `500` | Erro interno do servidor | Falha no processamento |

:::note Sobre os códigos apresentados

Os códigos `201`, `400`, `404` e `500` aparecem no documento da API.

O código `200` foi incluído para complementar a explicação dos resultados bem-sucedidos em HTTP.

A documentação não especifica todos os códigos possíveis para cada endpoint.

:::

## 3. Compreendendo objetos aninhados

Um objeto aninhado é um objeto JSON apresentado como valor de uma propriedade de outro objeto.

Considere:

```json
{
  "nome": "Pessoa Física Exemplo",
  "endereco": {
    "cep": "71000-000",
    "cidade": "Brasília",
    "uf": "DF"
  }
}
```

Nesse exemplo, `endereco` é uma propriedade da pessoa.

Entretanto, seu valor não é uma string ou um número.

O valor é outro objeto, contendo suas próprias propriedades.

Podemos representar essa organização da seguinte maneira:

```text
Pessoa Física
    │
    ├── nome
    │
    └── endereco
           │
           ├── cep
           ├── cidade
           └── uf
```

### 3.1. Acessando atributos aninhados

Em JavaScript, podemos acessar esses atributos utilizando a notação de ponto.

Considere:

```javascript
const pessoa = {
  nome: "Pessoa Física Exemplo",
  endereco: {
    cep: "71000-000",
    cidade: "Brasília",
    uf: "DF"
  }
};

console.log(pessoa.nome);

console.log(pessoa.endereco.cidade);
```

A primeira instrução acessa o atributo `nome`.

A segunda acessa o atributo `cidade`, que pertence ao objeto `endereco`.

**Resultado esperado:**

```text
Pessoa Física Exemplo
Brasília
```

Observe que a organização do JSON permite representar diferentes níveis de informações.

## 4. Estrutura do endereço

Na API de Pessoas, o endereço é representado por um objeto que contém diferentes atributos.

O exemplo de cadastro apresentado na documentação utiliza:

| Atributo | Descrição |

| `bairro` | Bairro |
| `cidade` | Cidade |
| `uf` | Unidade Federativa |
| `regiao` | Região do Brasil |

Exemplo:

```json
{
  "cep": "71000-000",

  "bairro": "Centro",
  "cidade": "Brasília",
  "uf": "DF",
  "regiao": "Centro-Oeste"
```

```json
{
  "nome": "Pessoa Física Exemplo",

  "endereco": {
    "cep": "71000-000",

    "cidade": "Brasília",
    "uf": "DF",
    "regiao": "Centro-Oeste"
  }
}
```

Observe que o endereço está associado à pessoa por meio da propriedade `endereco`.

Não precisamos repetir os atributos de endereço diretamente no nível principal do objeto.

Essa organização facilita a identificação das informações pertencentes a cada entidade.

## 5. Representando listas de telefones

Uma pessoa pode possuir diferentes telefones.

Por isso, a API utiliza um array para representar essa associação.

Considere:

```json
{
  "telefones": [
    {
      "ddd": "61",
      "numero": "998887776"
    },
    {
      "ddd": "61",
      "numero": "33445566"
    }
  ]
}
```

Observe que:

- `telefones` é o nome da propriedade;
- Os colchetes `[]` representam um array;
- Cada elemento do array é um objeto JSON;
- Cada telefone possui os atributos `ddd` e `numero`.

A estrutura pode ser representada da seguinte maneira:

```text
Pessoa
  │
  └── telefones [ ]
         │
         ├── Telefone 1
         │      ├── ddd
         │      └── numero
         │
         └── Telefone 2
                ├── ddd
                └── numero
```

### 5.1. Acessando os telefones em JavaScript

Considere:

```javascript
const pessoa = {
  nome: "Pessoa Física Exemplo",
  telefones: [
    {
      ddd: "61",
      numero: "998887776"
    },
    {
      ddd: "61",
      numero: "33445566"
    }
  ]
};

console.log(pessoa.telefones[0].numero);

console.log(pessoa.telefones[1].numero);
```

**Resultado esperado:**

```text
998887776
33445566
```

Observe que utilizamos índices para acessar os elementos do array.

O primeiro elemento possui índice `0`.

O segundo elemento possui índice `1`.

### 5.2. Percorrendo os telefones

Também podemos utilizar uma estrutura de repetição para acessar todos os telefones.

```javascript
pessoa.telefones.forEach((telefone) => {
  console.log(
    `(${telefone.ddd}) ${telefone.numero}`
  );
});
```

**Resultado esperado:**

```text
(61) 998887776
(61) 33445566
```

Esse exemplo demonstra como a representação em JSON pode ser manipulada utilizando recursos da linguagem JavaScript.

:::info JSON e JavaScript

JSON é um formato de representação de dados.

JavaScript possui objetos e arrays com estruturas semelhantes, mas JSON e objetos JavaScript não são exatamente a mesma coisa.

Por exemplo, em JSON, os nomes das propriedades precisam estar entre aspas duplas.

Em JavaScript, essas aspas nem sempre são necessárias.

:::

## 6. Representando o Título de Eleitor

A Pessoa Física possui um objeto associado chamado `titulo`.

Na documentação da API, esse objeto apresenta os seguintes atributos:

| Atributo | Descrição |
|---|---|
| `numero` | Número do Título de Eleitor |
| `zona` | Zona eleitoral |
| `secao` | Seção eleitoral |

Exemplo:

```json
{
  "numero": "123456",
  "zona": "001",
  "secao": "002"
}
```

Observe que esses valores foram representados como strings.

Isso permite preservar caracteres como zeros à esquerda.

Por exemplo, a zona eleitoral:

```json
"zona": "001"
```

não deve ser confundida com o número:

```json
"zona": 1
```

Embora os valores possam parecer semelhantes, a representação textual preserva exatamente a sequência informada.

### 6.1. Associação com Pessoa Física

O Título de Eleitor é apresentado dentro do documento de Pessoa Física:

```json
{
  "nome": "Pessoa Física Exemplo",
  "cpf": "12345678903",
  "titulo": {
    "numero": "123456",
    "zona": "001",
    "secao": "002"
  }
}
```

Na documentação da API, o Título de Eleitor é tratado como uma entidade vinculada à Pessoa Física.

Esse relacionamento também aparece no comportamento da operação de exclusão, que remove o título associado quando a Pessoa Física é excluída.

## 8. Representando a Inscrição Estadual

Na API, a Inscrição Estadual é representada pela propriedade `ie`.

O objeto contém:

| Atributo | Descrição |
|---|---|
| `numero` | Número da Inscrição Estadual |
| `estado` | Unidade Federativa |
| `dataRegistro` | Data de registro |

Exemplo:

```json
{
  "numero": "DF12345",
  "estado": "DF",
  "dataRegistro": "2023-01-01T00:00:00Z"
}
```

Observe que `dataRegistro` contém uma representação textual de data e hora.

### 8.1. Compreendendo a representação da data

Considere:

```text
2023-01-01T00:00:00Z
```

Essa representação segue o padrão ISO 8601.

Podemos identificar:

| Parte | Significado |
|---|---|
| `2023` | Ano |
| `01` | Mês |
| `01` | Dia |
| `T` | Separação entre data e hora |
| `00:00:00` | Hora, minuto e segundo |
| `Z` | Referência ao horário UTC |

Observe que a API apresenta a data como uma string JSON.

Isso é importante porque JSON não possui um tipo específico para representar datas.

### 8.2. Interpretando a data em JavaScript

Considere:

```javascript
const ie = {
  numero: "DF12345",
  estado: "DF",
  dataRegistro: "2023-01-01T00:00:00Z"
};

const data = new Date(ie.dataRegistro);

console.log(data.toISOString());
```

**Resultado esperado:**

```text
2023-01-01T00:00:00.000Z
```

O exemplo demonstra como uma string contendo data e hora pode ser interpretada pela linguagem JavaScript.

:::tip Datas e fusos horários

Ao apresentar datas e horários para usuários, é importante considerar o fuso horário.

Uma data representada em UTC pode ser apresentada de maneira diferente quando convertida para o horário local.

:::

## 9. Objetos aninhados e referências

Até o momento, utilizamos exemplos em que os dados relacionados estão apresentados diretamente dentro do documento principal.

Entretanto, a documentação da API informa que o serviço foi projetado para aceitar **objetos aninhados e referências por identificador**.

Vamos compreender essa diferença.

### 9.1. Objetos aninhados

Considere:

```json
{
  "nome": "Pessoa Física Exemplo",
  "endereco": {
    "cep": "71000-000",
    "cidade": "Brasília",
    "uf": "DF"
  }
}
```

Nesse caso, os dados do endereço estão apresentados diretamente dentro do objeto da pessoa.

Essa organização é chamada de representação aninhada.

### 9.2. Referências por identificador

Outra possibilidade é representar o relacionamento por meio de um identificador.

Considere o exemplo ilustrativo:

```json
{
  "nome": "Pessoa Física Exemplo",
  "endereco": "675b2e1b7a9d48a52b7a0005"
}
```

Nesse exemplo, o atributo `endereco` não contém diretamente os dados do endereço.

Ele contém uma referência para um registro identificado pelo valor informado.

### 9.3. Comparando as representações

**Objeto aninhado:**

```json
{
  "endereco": {
    "cep": "71000-000",
    "cidade": "Brasília"
  }
}
```

**Referência:**

```json
{
  "endereco": "675b2e1b7a9d48a52b7a0005"
}
```

Observe que ambas as representações permitem indicar uma associação entre pessoa e endereço.

Entretanto, apresentam estruturas diferentes.

:::note Sobre a API de Pessoas

A documentação informa que a API aceita tanto referências `_id` quanto objetos aninhados.

Os exemplos de cadastro apresentados no documento utilizam objetos aninhados.

O formato exato exigido para cada referência deve ser conferido na implementação do backend ou por meio de testes controlados. O exemplo de referência apresentado nesta seção é conceitual.

:::

## 10. Compreendendo o atributo _id

Nos exemplos de cadastro, não precisamos informar manualmente o identificador do novo registro.

Entretanto, nas respostas da API, os registros apresentam o atributo `_id`.

Considere o exemplo de resposta documentado para uma Pessoa Física:

```json
{
  "_id": "675b2e1b7a9d48a52b7a0009",
  "nome": "Leandro Vaguetti 3",
  "email": "leandro@ifb.edu.br",
  "cpf": "12345678903",
  "endereco": {
    "_id": "675b2e1b7a9d48a52b7a0005",
    "cep": "71000-000",
    "cidade": "Brasília"
  },
  "telefones": [
    {
      "_id": "675b2e1b7a9d48a52b7a0007",
      "ddd": "61",
      "numero": "998887776"
    }
  ],
  "titulo": {
    "_id": "675b2e1b7a9d48a52b7a0008",
    "numero": "123456"
  }
}
```

Observe que o atributo `_id` aparece em diferentes objetos.

Temos um identificador para a Pessoa Física e identificadores próprios para os objetos relacionados apresentados na resposta.

Isso permite distinguir as entidades envolvidas.

### 10.1. Identificador da pessoa

```json
"_id": "675b2e1b7a9d48a52b7a0009"
```

Identifica o registro da Pessoa Física.

### 10.2. Identificador do endereço

```json
"_id": "675b2e1b7a9d48a52b7a0005"
```

Identifica o endereço apresentado na resposta.

### 10.3. Identificador do telefone

```json
"_id": "675b2e1b7a9d48a52b7a0007"
```

Identifica o telefone apresentado.

### 10.4. Identificador do título

```json
"_id": "675b2e1b7a9d48a52b7a0008"
```

Identifica o Título de Eleitor.

:::info Identificadores e operações HTTP

O identificador da pessoa será importante nas operações de atualização e exclusão.

Por exemplo:

```http
PUT /pf/675b2e1b7a9d48a52b7a0009
```

ou:

```http
DELETE /pf/675b2e1b7a9d48a52b7a0009
```

Nesses casos, utilizamos o identificador da pessoa, e não o identificador de seu endereço ou telefone.

:::

## 11. Comparando os documentos de cadastro e resposta

Uma característica importante da comunicação com APIs é que o documento enviado pelo cliente pode ser diferente do documento retornado pelo servidor.

Vamos observar essa diferença.

### 11.1. Documento enviado no cadastro

Considere:

```json
{
  "nome": "Pessoa Física Exemplo",
  "email": "pessoa.fisica@exemplo.com",
  "cpf": "12345678903"
}
```

Esse documento representa as informações que o cliente deseja enviar.

### 11.2. Documento retornado pelo servidor

Uma resposta ilustrativa poderá apresentar:

```json
{
  "_id": "675b2e1b7a9d48a52b7a0009",
  "nome": "Pessoa Física Exemplo",
  "email": "pessoa.fisica@exemplo.com",
  "cpf": "12345678903"
}
```

Observe que o documento retornado apresenta o atributo `_id`.

Isso demonstra que o servidor pode acrescentar informações ao processar uma operação.

### 11.3. Por que os documentos podem ser diferentes?

Durante o processamento de uma requisição, o servidor pode:

- Gerar identificadores;
- Validar informações;
- Processar objetos associados;
- Recuperar dados relacionados;
- Organizar a representação enviada na resposta.

Os exemplos da API mostram que as respostas de cadastro incluem identificadores que não aparecem nos documentos enviados.

Entretanto, o comportamento exato depende da implementação do serviço.

## 12. Relações entre as entidades

A estrutura apresentada na documentação permite identificar diferentes associações.

Podemos representar conceitualmente essas relações da seguinte maneira:

```text
                   PESSOA
                      │
           ┌──────────┴──────────┐
           │                     │
           ▼                     ▼
     PESSOA FÍSICA        PESSOA JURÍDICA
           │                     │
           ├── Endereço          ├── Endereço
           │                     │
           ├── Telefones         ├── Telefones
           │                     │
           └── Título            └── Inscrição
               Eleitoral             Estadual
```

A documentação informa que:

- A Pessoa Física possui um Título de Eleitor associado;
- A Pessoa Jurídica possui uma Inscrição Estadual associada;
- Telefones e endereços podem ser entidades compartilhadas;
- A exclusão de uma Pessoa Física remove seu título vinculado;
- A exclusão de uma Pessoa Jurídica remove sua inscrição estadual vinculada;
- Telefones e endereços compartilhados não são excluídos automaticamente nessas operações.

Essas características serão importantes quando estudarmos os endpoints de exclusão.

:::tip Relacionamentos entre entidades

Uma associação entre entidades pode ser representada de diferentes maneiras em uma API.

A representação enviada ou recebida em JSON não determina, por si só, como os dados são armazenados internamente.

Por isso, devemos distinguir a estrutura de comunicação da implementação do banco de dados.

:::

## 1. Conhecendo os endpoints de Pessoa Física

A API de Pessoas disponibiliza um conjunto de operações para manipulação dos registros de Pessoas Físicas.

A URL base do serviço é:

https://backend-pessoas.vercel.app/

Os endpoints utilizados são:

| Método HTTP | Endpoint | Finalidade |
|---|---|---|
| `GET` | `/pf` | Listar Pessoas Físicas |
| `GET` | `/pf/filtrar?nome=texto` | Filtrar Pessoas Físicas pelo nome |
| `POST` | `/pf` | Cadastrar uma Pessoa Física |
| `PUT` | `/pf/:id` | Atualizar uma Pessoa Física |
| `DELETE` | `/pf/:id` | Excluir uma Pessoa Física |

Observe que algumas operações utilizam o mesmo endpoint.

Por exemplo:

```http
GET /pf
```

e:

```http
POST /pf
```

Embora utilizem o mesmo recurso, representam operações diferentes.

O método `GET` solicita uma consulta, enquanto o método `POST` solicita a criação de um registro.

:::tip Método HTTP e endpoint

Para compreender uma operação REST, precisamos observar dois elementos:

- **Método HTTP:** indica o que desejamos fazer;
- **Endpoint:** indica o recurso com o qual desejamos trabalhar.

:::

## 3. Filtrando Pessoas Físicas pelo nome

```http
GET
```

```text
/pf/filtrar
```

**Parâmetro de consulta:**

```text
nome
```

```http
GET /pf/filtrar?nome=ana
```

## 7. Excluindo uma Pessoa Física — DELETE /pf/:id

A operação de exclusão utiliza o método HTTP `DELETE`.

Essa operação solicita ao servidor a remoção de um registro existente.

### 7.1. Estrutura da requisição

**Método:**

```http
DELETE
```

**Endpoint:**

```text
/pf/:id
```

Considere:

```http

```

Observe que o identificador da Pessoa Física é informado diretamente na URL.

### 7.2. O que acontece na exclusão?

De acordo com a documentação da API, a exclusão de uma Pessoa Física também remove seu Título de Eleitor associado.

Entretanto, telefones e endereços compartilhados não são excluídos automaticamente.

Podemos representar esse comportamento da seguinte maneira:

```text
           PESSOA FÍSICA
                 |
                 | DELETE /pf/:id
                 v
              API REST
                 |
          ┌──────┴──────┐
          |             |
          v             v
     Remove PF     Remove Título
                    de Eleitor
```

Os registros de endereço e telefone não são removidos automaticamente por essa operação, conforme descrito na documentação.

### 7.3. Cuidados com a exclusão

Uma exclusão pode modificar permanentemente os dados armazenados no servidor.

Por isso, devemos ter cuidado ao executar essa operação.

Durante as atividades práticas:

1. Cadastre uma Pessoa Física fictícia;
2. Registre o identificador retornado;
3. Utilize esse identificador para testar a exclusão;
4. Consulte novamente a listagem para verificar o resultado.

:::warning Operação de exclusão

Não exclua registros que não tenham sido criados por você para a atividade.

Como a API está publicada, outras pessoas também poderão estar utilizando o serviço.

## 5. Compreendendo a data de registro da Inscrição Estadual

A documentação apresenta a data de registro da Inscrição Estadual no seguinte formato:

```json
"dataRegistro": "2023-01-01T00:00:00Z"
```

Esse valor é uma string que representa uma data e um horário.

O formato utilizado segue o padrão ISO 8601.

Podemos interpretar seus elementos da seguinte maneira:

```text
2023-01-01T00:00:00Z
│    │  │ │  │  │  │
│    │  │ │  │  │  └── Referência UTC
│    │  │ │  │  └───── Segundos
│    │  │ │  └──────── Minutos
│    │  │ └─────────── Horas
│    │  └───────────── Separador T
│    └──────────────── Dia e mês
└───────────────────── Ano
```

A tabela abaixo apresenta os elementos com mais detalhes:

| Elemento | Valor | Significado |
|---|---|---|
| Ano | `2023` | Ano do registro |
| Mês | `01` | Janeiro |
| Dia | `01` | Primeiro dia do mês |
| Separador | `T` | Separa data e hora |
| Horário | `00:00:00` | Meia-noite |
| Fuso | `Z` | Horário UTC |

### 5.1. Por que a data é enviada como texto?

O formato JSON possui tipos como:

- String;
- Número;
- Booleano;
- Objeto;
- Array;
- `null`.

Entretanto, JSON não possui um tipo específico para datas.

Por isso, é comum representar datas utilizando strings padronizadas.

### 5.2. Interpretando a data em JavaScript

Considere:

```javascript
const ie = {
  numero: "DF12345",
  estado: "DF",
  dataRegistro: "2023-01-01T00:00:00Z"
};

const data = new Date(ie.dataRegistro);

console.log(data.toISOString());
```

**Resultado esperado:**

```text
2023-01-01T00:00:00.000Z
```

Observe que a linguagem JavaScript permite converter a representação textual em um objeto `Date`.

:::tip Datas e horários

Ao trabalhar com datas, devemos considerar a diferença entre o horário UTC e o horário local.

O caractere `Z` indica que o horário informado está representado em UTC.

:::

De acordo com a documentação, a exclusão de uma Pessoa Jurídica também remove sua Inscrição Estadual associada.

Entretanto, endereços e telefones compartilhados não são excluídos automaticamente.

Podemos representar esse comportamento da seguinte maneira:

```text
          PESSOA JURÍDICA
                 |
                 | DELETE /pj/:id
                 v
              API REST
                 |
          ┌──────┴──────┐
          |             |
          v             v
     Remove PJ      Remove IE
```

Essa operação possui comportamento semelhante à exclusão de Pessoas Físicas.

A diferença está no objeto específico associado a cada tipo de pessoa.

### 8.3. Comparando as exclusões

| Recurso | Registro principal removido | Objeto específico removido |
|---|---|---|
| Pessoa Física | Pessoa Física | Título de Eleitor |
| Pessoa Jurídica | Pessoa Jurídica | Inscrição Estadual |

A documentação informa que endereços e telefones compartilhados não são removidos automaticamente nessas operações.

## 11. Atividade 10 — Interpretando erros HTTP

## 16. Considerações finais

A comunicação com APIs REST é um conhecimento importante no desenvolvimento de sistemas.

Ao compreender como construir requisições HTTP e interpretar respostas, podemos utilizar serviços disponibilizados por diferentes aplicações, independentemente da linguagem ou tecnologia utilizada para implementá-los.

Neste capítulo, nosso objetivo foi compreender **como utilizar uma API existente**.

Não foi necessário desenvolver o frontend nem implementar o backend.

Essa separação permite estudar o funcionamento dos serviços antes de conhecer os detalhes de sua implementação.

Os conhecimentos desenvolvidos aqui servirão de referência para estudos posteriores, especialmente em dois contextos:

**Integração com aplicações frontend:** utilização de requisições HTTP para conectar interfaces aos serviços disponibilizados pela API.

**Desenvolvimento de backend:** implementação dos endpoints, processamento das requisições e gerenciamento dos dados utilizados pela aplicação.

Assim, concluímos o estudo da comunicação com a API REST de gerenciamento de Pessoas Físicas e Jurídicas, estabelecendo uma base para compreender tanto o consumo quanto a construção de serviços HTTP.
